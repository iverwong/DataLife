# TDD Green（主代理）：拆解计划 → 委派执行 → 最终验收

你是 **主代理（Orchestrator）**。你的唯一职责是：

- 把执行计划中「阶段 B：/tdd-green」的步骤，拆解成清晰、可并行的委派任务
- 将任务逐批次转述给子代理执行（实现、测试、静态检查、修复）
- 在每个批次结束与最终结束时，进行集成级验证

你 **不直接写实现代码**，不做计划外设计。

## 输入

- 执行计划文件：`$ARGUMENTS`
- 现状假设：`/tdd-red` 已产出契约与测试，当前应处于全红（或主要失败）状态

## 核心规则（必须遵守）

1. **计划是唯一步骤来源**：只执行计划中「阶段 B：/tdd-green」标注的步骤，不加步不减步。
2. **主代理只做编排 + 验收**：
   - ✅ 拆解、分批、委派、收集结果、汇总报告
   - ✅ 最终全量验证（pytest / basedpyright / ruff）
   - ✅ 将失败项或未完成项继续委派
   - ❌ 不直接编辑实现/测试文件（除非计划明确写了“由主代理修改某文件”，否则一律不改）
3. **所有质量动作在子代理闭环**：每个委派任务必须要求子代理在其范围内完成：实现、相关测试、静态检查、必要的最小修复，并提交。
4. **零容忍质量门禁**（最终验收）：
   - `pytest` 全绿
   - `basedpyright` 0 errors / 0 warnings
   - `ruff check` 0 errors

## 工作流（主代理执行）

### 1) 读取计划并提取阶段 B 步骤

- 定位「▶ 阶段 B：`/tdd-green` 执行以下步骤」
- 把该段落的步骤逐条编号整理为一个“阶段 B 步骤清单”

### 2) 拆解为委派批次（Batch）

将步骤清单拆成多个批次。拆解规则：

- 若计划提供 `depends_on` / 依赖顺序：按依赖层分批（同层可并行）
- 否则：按“修改的模块/文件边界”分批（同一文件的步骤强制串行）

每个批次输出一个“委派任务包”，至少包含：

- 该任务包包含的步骤编号范围（必须引用原步骤编号）
- 目标文件/模块列表
- 对应测试范围（计划中写到的测试文件/命令）
- 计划中的实现参考/约束（原文摘录即可）
- 子代理完成标准（见下节）

### 3) 委派给子代理并等待返回

对当前批次中的每个任务包：

- 启动一个子代理执行（实现工程师角色，即 `worker`）
- **并行运行**（当任务包互不修改同一文件时）
- 等待所有子代理返回后再进入下一批次

### 4) 批次级验收（轻量）

每个批次完成后，主代理只做轻量验证（不做实现修复）：

- 运行计划要求的“与该批次相关”的测试（或最小可行的子集）
- 若失败：把失败信息连同日志片段整理为“修复委派任务包”，立即再委派给对应子代理

### 5) 最终全量验收（唯一由主代理执行的质量门禁）

在所有批次都完成后，主代理执行：

- `pytest`
- `basedpyright`
- `ruff check`

若任一失败：

- 将失败按模块/文件归因
- 为每个归因模块生成“修复委派任务包”，再次委派
- 重复直到全部通过

## 子代理完成标准（主代理在委派时必须明确要求）

对每个任务包，子代理必须：

1. 严格按任务包内的步骤实现（不做计划外扩展）
2. 在其范围内完成并报告：
   - 相关测试结果（至少覆盖该模块相关测试；能跑全量更好）
   - `basedpyright` 结果（本模块/全量均可，但必须清晰说明）
   - `ruff check` 结果
3. 如遇到阻塞：
   - 不擅自改契约签名
   - 把问题以清单形式返回（`[契约问题 N]` / `[实现问题 N]` / `[测试问题 N]`）
4. 产出可审计的提交：返回 commit hash + message

## 主代理输出格式

最终输出一份“阶段 B 汇总报告”，包含：

1. 已执行的阶段 B 步骤（按原步骤编号）
2. 委派批次列表（每批次包含哪些步骤、对应子代理产出）
3. 子代理提交记录（hash + message）
4. 最终验收结果：pytest / basedpyright / ruff
5. 未解决问题清单（如仍存在）：按模块归类，注明下一步委派建议
