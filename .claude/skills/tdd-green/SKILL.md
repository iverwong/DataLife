# TDD Green（主代理）：拆解计划 → 委派执行 → 最终验收

你是 **主代理（Orchestrator）**。你的唯一职责是：

- 确认在特性分支上
- 读取执行计划阶段 B，按文件拆分为独立任务
- 将每个文件的任务委派给子代理并行执行
- 批次级验收 + 最终全量验证 + 失败项再委派

你 **不直接写实现代码**，不做计划外设计。

## 输入

- 执行计划文件：`$ARGUMENTS`
- 现状假设：`/tdd-red` 已产出契约与测试，当前应处于全红（或主要失败）状态

## 核心规则

1. **计划是唯一步骤来源**：只执行计划中「阶段 B：/tdd-green」标注的步骤，不加步不减步
2. **主代理只做编排 + 验收**：
   - ✅ 分支检查、拆解、委派、收集结果、汇总报告
   - ✅ 最终全量验证（pytest / basedpyright / ruff）
   - ✅ 将失败项或未完成项继续委派
   - ❌ 不直接编辑实现/测试文件
3. **一个文件 = 一个子代理**：计划阶段 B 中每个文件章节，独立委派给一个子代理
4. **所有质量动作在子代理闭环**：每个子代理在其范围内完成实现、测试、静态检查、必要修复

## 工作流

### 1) 分支检查

确认当前在特性分支上（非 master）：

```
git branch --show-current
```

若不在特性分支，提示用户先执行 `/tdd-red` 或手动切换分支。

### 2) 读取计划并按文件拆分

定位计划的阶段 B 部分（实现步骤），提取每个文件章节的内容。

按文件拆分为独立的子代理任务。有依赖关系的文件按依赖层分批：

- **无依赖的文件**可并行（同一批次）
- **有依赖的文件**按依赖顺序串行（后续批次）
- **同一文件内的步骤**强制串行（由同一个子代理完成）

### 3) 委派给子代理

对每个文件创建一个子代理任务，传递以下上下文：

**必须包含的上下文：**

- **目标文件路径**
- **需实现的函数列表**：从计划对应文件章节摘录的函数名、实现说明或实现代码
- **Red 阶段已写入的契约**：该文件中已有的函数签名和 docstring（子代理需要看到完整契约才能实现）
- **对应的测试文件和测试命令**：子代理实现后用于验证
- **依赖接口**：该文件 import 的其他文件的函数签名（只需签名，让子代理知道接口形状）
- **三方库参考**：如该文件涉及三方库，摘录计划中的相关用法和注意事项

**子代理完成标准：**

1. 严格按计划内容实现（不做计划外扩展）
2. 运行对应的测试并确认通过
3. 运行 `basedpyright` 和 `ruff check` 覆盖本文件和对应测试文件
   - **零容忍**：所有 error 和 warning 必须消除
   - 如 warning 确有合理原因（如三方库类型存根缺失），使用 `type: ignore[<rule>]` 并附注释说明原因（包括 Any、Unknown 等常被忽略的警告）
4. 如遇阻塞：
   - 不擅自改契约签名
   - 把问题以清单形式返回：`[契约问题 N]` / `[实现问题 N]` / `[测试问题 N]`
5. 产出可审计的提交：返回 commit hash + message

### 4) 批次级验收

每个批次的子代理全部返回后，主代理做轻量验证：

- 运行该批次相关的测试
- 若失败：把失败信息整理为"修复委派任务包"，再委派给对应子代理
- 通过后进入下一批次

### 5) 最终全量验证

所有批次完成后，主代理执行：

```
./venv/Scripts/python -m pytest
./venv/Scripts/python -m basedpyright <所有涉及的源码和测试文件>
./venv/Scripts/python -m ruff check <所有涉及的源码和测试文件>
```

- **零容忍**：pytest 全绿 + basedpyright 0 errors / 0 warnings + ruff 0 errors

若任一失败：

- 将失败按文件归因
- 为每个文件生成"修复委派任务包"，再次委派
- 重复直到全部通过

## 输出格式

最终输出"阶段 B 汇总报告"：

1. 已执行的阶段 B 步骤（按计划中的文件章节）
2. 委派批次列表（每批次包含哪些文件、对应子代理产出）
3. 子代理提交记录（hash + message）
4. 最终验收结果：pytest / basedpyright / ruff
5. 未解决问题清单（如仍存在）：按文件归类，注明下一步建议
