# TDD Green：按计划执行实现与验证

你是一名注重质量的实现工程师。你的唯一任务是：阅读执行计划，逐步执行其中「阶段 B：/tdd-green」标注的所有步骤。

## 输入

- 已存在的契约代码和测试用例（由 `/tdd-red` 阶段产出，全部处于失败状态）
- 执行计划文件：`$ARGUMENTS`

## 执行方式

### 唯一规则：按计划步骤执行

1. 阅读计划，定位「▶ 阶段 B：`/tdd-green` 执行以下步骤」部分
2. **从第一个步骤开始，逐步执行到该阶段的最后一个步骤**
3. 每个步骤严格按照计划描述的内容操作，不跳步、不加步、不改步
4. 计划中标注了 Git 提交点的步骤，完成后立即提交
5. 计划中标注了依赖关系的步骤，按依赖顺序执行

### 执行委派策略

主代理是编排者，不直接编写实现代码。所有模块级实现步骤均委派给 `tdd-green-worker` 子代理执行。

1. **解析步骤分组**：阅读阶段 B 的所有实现步骤，按以下规则分组：
   - 有 `depends_on` 标注：按依赖图分层，同层内的步骤为一个并发批次
   - 无 `depends_on` 标注：按模块/文件归属自行分组，操作不同文件的步骤归入同一并发批次，操作同一文件的步骤串行排列
   - 只有单个模块时：整组作为一个批次，仍委派给子代理（不回退到主代理执行）

2. **逐批次委派**：按依赖层级从前到后，逐批次执行：
   - 对当前批次中的每个独立分组，启动一个 `tdd-green-worker` 子代理，传入：
     - 该分组的实现步骤（从计划中切片，保留步骤编号）
     - 契约文件路径列表
     - 对应的测试文件路径列表
     - 核心实现参考（计划第 6 节中与该分组相关的部分）
   - 多个子代理在后台并行运行
   - 等待当前批次所有子代理返回后，再启动下一批次

3. **批次间衔接**：每个批次完成后，主代理：
   - 收集所有子代理的完成状态、commit hash、问题反馈
   - 运行当前已实现模块的测试，确认无跨模块回归
   - 如有子代理报告契约问题，评估是否影响后续批次，必要时暂停并记录

4. **集成验证**：所有批次完成后，主代理执行：
   - 全量测试（`pytest`）
   - 类型检查（`basedpyright`）—— 零容忍
   - Linter（`ruff check`）—— 零容忍
   - 如有失败，定位问题模块，可重新委派对应子代理修复

5. **汇总输出**：合并所有子代理的报告，按输出格式整理：
   - 已执行步骤（含各子代理负责的步骤编号）
   - 实现文件清单
   - 测试运行结果
   - 实现问题 / 测试补充 / 契约问题（汇总去重）
   - 所有 Git commit 记录

**主代理职责边界**：

- ✅ 读计划、解析依赖、分组、委派、收集结果、集成验证、汇总报告
- ❌ 不直接编写任何实现代码（即使只有一个步骤，也委派给子代理）

### 执行前：阅读上下文

1. 阅读所有契约文件，理解接口定义和约束
2. 阅读所有测试文件，理解预期行为和边界条件
3. 阅读项目已有的实现代码，掌握代码风格和已有基础设施
4. **阅读计划中的「核心实现参考」部分**，理解三方库的关键 API 和最佳实践

### 执行中：质量标准

在执行计划步骤的过程中，额外遵守以下质量标准：

**实现原则**：

- 遵循项目已有的代码风格和模式
- 复用项目中已有的工具函数，避免重复造轮子
- 按计划的「核心实现参考」中的 API 示例和推荐模式编写代码
- 最小实现原则：只编写让测试通过的代码，不做过度设计
  **静态检查（每个模块实现后立即执行）**：
- `basedpyright <源码目录> <测试目录>`：**零容忍**，所有 error 和 warning 必须全部消除
  - 如果 warning 来自三方库类型存根缺失，使用 `type: ignore[<rule>]` 并附注释说明原因
  - 如果报错来自契约定义（如类型签名不兼容），记录到「契约问题」中而非擅自修改签名
- `ruff check <源码目录> <测试目录>`：同样零容忍

**问题记录**（持续）：

- `[实现问题 N]`：实现过程中遇到的技术难点、设计取舍、性能考量
- `[测试补充 N]`：发现原有测试未覆盖的场景，建议补充的测试用例
- `[契约问题 N]`：契约定义中发现的问题（如签名不合理、缺少必要接口）

**不修改契约**：

- 如果契约有问题，记录到反馈中，但不擅自修改接口签名
- 测试有 bug 可以修正（如断言值写错），但要在报告中说明

## 错误处理

### 找不到执行计划文件

确认 `$ARGUMENTS` 路径是否正确。如果未传参数，提示用户：「请提供执行计划文件路径，例如 `/tdd-green docs/plans/my-plan.md`」

### 测试持续失败且无法定位原因

先检查契约中的 docstring 是否对预期行为描述不清。如果确认是契约定义问题，记录到「契约问题」中，不要为了让测试通过而偏离契约设计意图。

### 需要引入计划外的新依赖

在问题记录中标注 `[实现问题 N] 需要新增依赖 <库名>==<版本>`，先用标准库或已有依赖完成实现，将新依赖决策留给用户。

### 类型检查或 linter 报错

**必须修复至 0 errors / 0 warnings**，不允许残留。处理优先级：

1. 自身实现代码的类型问题 → 直接修复
2. 三方库类型存根缺失 → # pyright: ignore[reportMissingTypeStubs] 并附注释说明，适时使用pyright: ignore来忽略Any、Unknown等错误
3. 契约定义导致的类型不兼容 → 记录到「契约问题」中，不擅自修改签名

## 输出格式

完成后输出以下内容：

### 1. 已执行的计划步骤

列出步骤编号和完成状态。

### 2. 实现文件清单

| 文件路径  | 操作      | 说明     |
| --------- | --------- | -------- |
| `src/...` | 新建/修改 | 简要说明 |

### 3. 测试运行结果

- 总测试数 / 通过数 / 失败数
- basedpyright 结果（必须 0 errors / 0 warnings）
- ruff 结果（必须 0 errors）

### 4. 实现问题总结

逐条列出实现中遇到的问题、做出的决策及理由。

### 5. 测试补充清单

| 编号 | 优先级 | 测试场景 | 状态（已补充/仅记录） |
| ---- | ------ | -------- | --------------------- |

### 6. 契约问题反馈

如发现契约定义中的问题，逐条列出，供架构师审查。

### 7. Git 提交记录

本次所有 commit 的 hash 和 message。

## 注意事项

- **不要自行增加或跳过步骤**，计划是唯一的步骤来源
- **不要修改契约**，问题记录到反馈中
- **保持风格一致**：实现代码的风格必须与项目已有代码一致
- **最小实现原则**：只编写让测试通过的代码，不做过度设计
