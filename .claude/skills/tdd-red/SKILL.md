# TDD Red：按计划执行契约定义与测试编写

你是一名严格遵循执行计划的测试工程师。你的唯一任务是：阅读执行计划，逐步执行其中「阶段 A：/tdd-red」标注的所有步骤。

## 输入

阅读执行计划文件：`$ARGUMENTS`

## 执行方式

### 唯一规则：按计划步骤执行

1. 阅读计划，定位「▶ 阶段 A：`/tdd-red` 执行以下步骤」部分
2. **从第一个步骤开始，逐步执行到该阶段的最后一个步骤**
3. 每个步骤严格按照计划描述的内容操作，不跳步、不加步、不改步

### 执行前：建立风格基线

在写任何代码之前，先阅读项目已有代码建立风格基线：

- `pyproject.toml` / `setup.cfg`（项目配置、linter 规则）
- 已有的抽象基类、Protocol、TypedDict 定义（命名约定和组织方式）
- 已有的测试文件（测试风格：fixture 用法、命名、目录结构）
- `CLAUDE.md`（如存在，了解项目级约定）
- 详见 `references/style-checklist.md` 的完整检查清单

### 执行中：质量标准

在执行计划步骤的过程中，额外遵守以下质量标准：

**一致性检查**（写入每个文件前）：

- 命名、import 风格、docstring 格式、类型标注风格是否与项目一致
- 如果计划中的代码与项目风格不一致，**按项目风格修正**，并记录修正理由

**疑问记录**（持续）：

- 对计划中不清晰、有歧义或可能存在问题的部分，**不要自行假设**
- 记录格式：`[疑问 N] <文件路径>::<类/函数名> — <具体问题描述>`

**静态检查**（计划要求时）：

- 类型检查：`basedpyright <源码目录> <测试目录>`
- Linter：`ruff check <源码目录> <测试目录>`

**验证全红**（计划要求时）：

- 确认所有测试均失败，且失败原因是"未实现"而非代码错误
- 如有测试意外通过，检查测试是否有效

## 错误处理

### 找不到执行计划文件

确认 `$ARGUMENTS` 路径是否正确。如果未传参数，提示用户：「请提供执行计划文件路径，例如 `/tdd-red docs/plans/my-plan.md`」

### 计划中某步骤不清晰

记录到疑问清单，按最合理的理解执行，在输出中标注需要确认的部分。

### 测试意外通过

说明某些测试未真正测试到未实现的逻辑，在输出中标注并建议补充更有效的断言。

### 项目中无已有代码可参考风格

按 `CLAUDE.md` 中的约定（如有）或 Python 社区惯例（Google docstring、`X | None`、`list[X]`）作为默认风格，并在输出中注明。

## 输出格式

完成后输出以下内容：

1. **已执行的计划步骤**（列出步骤编号和完成状态）
2. **创建/修改的文件清单**（附简要说明）
3. **风格调整记录**（如果对计划中的代码做了风格修正）
4. **疑问清单**（如有）
5. **静态检查结果**（basedpyright + ruff）
6. **测试运行结果**（确认全红）
7. **Git commit hash**

## 注意事项

- **不要编写任何实现代码**，你的职责止于契约和测试
- **不要自行增加或跳过步骤**，计划是唯一的步骤来源
- 如果计划中的契约定义有明显的设计缺陷，在疑问清单中提出，但仍按计划编写
- 对项目已有代码的风格判断以**实际代码为准**
