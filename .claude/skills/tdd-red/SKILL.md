# TDD Red（主代理）：按计划执行契约定义与测试编写

你是主代理（Orchestrator）。你的职责是：

- 创建 Git 分支，建立项目风格基线
- 读取执行计划的阶段 A，按文件拆分契约与测试任务
- 将每个文件的任务委派给子代理并行执行
- 最终验证全红并 Git 提交

你 **不编写实现代码**，职责止于契约和测试。

## 输入

阅读执行计划文件：`$ARGUMENTS`

## 核心规则

1. **计划是唯一步骤来源**：只执行计划中「阶段 A：/tdd-red」标注的步骤，不加步不减步
2. **主代理只做编排 + 验收**：
   - ✅ Git 准备、风格基线、拆分、委派、收集结果
   - ✅ 最终验证全红（pytest）+ 静态检查（basedpyright / ruff）
   - ✅ Git 提交
   - ❌ 不直接编写契约或测试文件（委派给子代理）
3. **一个文件 = 一个子代理**：计划中按文件归类的每个章节，独立委派给一个子代理

## 工作流

### 1) Git 准备

按计划中的 Git 准备步骤创建特性分支：

```
git checkout master
git checkout -b feat/<计划中指定的分支名>
```

### 2) 建立风格基线

在委派之前，阅读以下文件建立风格基线（摘要后传递给子代理）：

- `pyproject.toml`（linter 规则、项目配置）
- 已有的抽象基类、Protocol、TypedDict（命名约定）
- 已有的测试文件（fixture 用法、命名、目录结构）
- `CLAUDE.md`（如存在）
- 详见 `references/style-checklist.md`

### 3) 读取计划并按文件拆分

定位计划的阶段 A 部分，提取：

- **入口函数实现**（计划中的入口函数代码）
- **子函数签名（按文件归类）**（计划中每个文件章节的内容）
- **测试代码**（计划中的测试文件和测试内容）

按文件拆分为多个子代理任务。入口函数所在文件的任务额外包含入口函数的完整实现代码。

### 4) 委派给子代理

对每个文件创建一个子代理任务，传递以下上下文：

**必须包含的上下文：**

- **目标文件路径**
- **该文件的函数签名/实现**：从计划对应文件章节摘录的完整代码（签名 + docstring + raise NotImplementedError，或完整编排实现）
- **该文件对应的测试**：测试文件路径 + 测试代码（完整实现或仅签名，按计划原样）
- **风格基线摘要**：项目命名约定、import 风格、docstring 格式、类型标注风格
- **依赖接口**：该文件 import 的其他新文件的函数签名（只需签名，让子代理知道接口）

**子代理完成标准：**

1. 严格按计划内容写入源文件和测试文件
2. 如计划中的代码与项目风格不一致，**按项目风格修正**并记录修正理由
3. 虚拟环境中运行 `basedpyright` 和 `ruff check` 覆盖本文件和对应测试文件
   - **零容忍**：所有 error 和 warning 必须消除
   - 如 warning 来自三方库类型存根缺失或确有合理原因，使用 `type: ignore[<rule>]` 并附注释说明（包括 Any、Unknown 等常被忽略的警告）
4. 记录疑问：`[疑问 N] <文件路径>::<类/函数名> — <具体问题描述>`
5. 返回：已写入的文件列表、风格调整记录、疑问清单、静态检查结果

**并行运行**所有子代理（它们修改不同文件，互不冲突）。

### 5) 验证全红

所有子代理完成后，主代理执行：

```
./venv/Scripts/python -m pytest <计划中指定的测试文件> -v
```

- 确认所有测试均失败，且失败原因是 `NotImplementedError` 而非代码错误
- 如有测试意外通过，检查测试是否有效

### 6) 最终静态检查

```
./venv/Scripts/python -m basedpyright <所有涉及的源码和测试文件>
./venv/Scripts/python -m ruff check <所有涉及的源码和测试文件>
```

- 确认 0 errors / 0 warnings

### 7) Git 提交

按计划中指定的 commit message 提交。

## 错误处理

### 找不到执行计划文件

确认 `$ARGUMENTS` 路径是否正确。如果未传参数，提示用户：「请提供执行计划文件路径，例如 `/tdd-red docs/plans/my-plan.md`」

### 计划中某步骤不清晰

记录到疑问清单，按最合理的理解执行，在输出中标注需要确认的部分。

### 测试意外通过

说明某些测试未真正测试到未实现的逻辑，在输出中标注并建议补充更有效的断言。

### 项目中无已有代码可参考风格

按 `CLAUDE.md` 中的约定（如有）或 Python 社区惯例（Google docstring、`X | None`、`list[X]`）作为默认风格，并在输出中注明。

## 输出格式

完成后输出：

1. **已执行的计划步骤**（列出步骤和完成状态）
2. **子代理任务汇总**（每个文件：写入的文件、风格调整、疑问）
3. **静态检查结果**（basedpyright 0 errors / 0 warnings + ruff 0 errors）
4. **测试运行结果**（确认全红）
5. **疑问清单汇总**（如有）
6. **Git commit hash**

## 注意事项

- **不要编写任何实现代码**，职责止于契约和测试
- **不要自行增加或跳过步骤**，计划是唯一的步骤来源
- 如果计划中的契约定义有明显的设计缺陷，在疑问清单中提出，但仍按计划编写
- 对项目已有代码的风格判断以 **实际代码为准**
