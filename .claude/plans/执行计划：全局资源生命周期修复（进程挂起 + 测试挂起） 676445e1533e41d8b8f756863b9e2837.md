# 执行计划：全局资源生命周期修复（进程挂起 + 测试挂起）

## 1. 修复目标

修复 DataLife 项目中**全局异步资源未正确关闭**导致的两个挂起问题：

- **进程挂起**：`asyncio.run(main())` 完成后，Python 进程因非 daemon 线程存活而无法退出
- **测试挂起**：`pytest` 运行完毕后，测试进程因未关闭的 aiosqlite 连接和 httpx 客户端而无法退出

---

## 2. 问题来源

本修复基于代码审查发现的 4 个资源泄露点：

| **编号** | **问题** | **位置** | **影响范围** |
| --- | --- | --- | --- |
| P1 | `httpx.AsyncClient` 全局单例从未调用 `aclose()` | `core/notion/client.py` 末尾 | 进程挂起 |
| P2 | `aiosqlite.Connection` 全局单例从未关闭 | `core/db/__init__.py` → `_get_db()` | 进程挂起（主因：aiosqlite 后台线程为非 daemon） |
| P3 | `in_memory_db` fixture 每次调用创建新连接，从不关闭 | `tests/conftest.py` → `in_memory_db()` | 测试挂起 |
| P4 | 模块级 `httpx.AsyncClient` 在 import 时创建，测试结束后未关闭 | `core/notion/client.py`（被测试文件间接 import） | 测试挂起 |

### 挂起机制详解

<aside>
🔍

**进程挂起的本质**：`asyncio.run(main())` 本身会正常返回（事件循环中无待完成的 awaitable），但 Python 进程默认等待所有**非 daemon 线程**结束才退出。`aiosqlite` 内部驱动 SQLite 的线程是非 daemon 线程，不关闭连接 = 线程永远存活 = 进程永远不退出。

</aside>

<aside>
🔍

**测试挂起的本质**：

1. `in_memory_db` fixture 将 `core.db._get_db` patch 为 `_get_test_db`，但 `_get_test_db` 每次被调用都创建一个**新的** `aiosqlite.connect(":memory:")` 连接（绕过了原始 `_get_db` 的单例缓存），且这些连接在 fixture teardown 时**从未被关闭**，累积的后台线程导致进程挂起
2. 测试文件 import `core.handlers.business` 时会间接触发 `core/notion/client.py` 的模块级代码执行，创建全局 `httpx.AsyncClient`，测试结束后该客户端未关闭
</aside>

- `depends_on: none`
- **问题类别**：资源泄露修复
- **目标文件**：`core/notion/client.py`
- **描述**：
    - 在文件末尾添加 `async def close_client() -> None` 函数
    - 函数内部：先调用 `await httpx_client.aclose()`，然后记录 debug 日志
    - 幂等性保护：调用前检查 `httpx_client.is_closed`，若已关闭则跳过
    - 将 `close_client` 加入模块的公开 API（如有 `__all__` 则添加）
- **验证**：运行 `pytest tests/test_resource_cleanup.py::test_close_client_exists_and_works tests/test_resource_cleanup.py::test_close_client_idempotent -v`，确认通过

### 步骤 2：为 `core/db/__init__.py` 添加 `close_db()` 函数

- `depends_on: none`
- **问题类别**：资源泄露修复
- **目标文件**：`core/db/__init__.py`
- **描述**：
    - 添加 `async def close_db() -> None` 函数
    - 函数内部：检查全局 `db` 是否为 `None`，若非 `None` 则调用 `await db.close()`，之后将 `db` 重置为 `None`

### 步骤 3：在 `main.py` 的 `main()` 中添加资源清理

- `depends_on: [步骤 1, 步骤 2]`
- **问题类别**：资源泄露修复
- **目标文件**：`main.py`
- **描述**：
    - 在 `main()` 函数中，用 `try/finally` 包裹整个业务逻辑
    - `finally` 块中按顺序调用：先 `await close_client()`（上层），再 `await close_db()`（底层）

    - 关闭顺序的理由：先关闭 HTTP 客户端确保不再有新的 DB 写入请求，再关闭数据库
- **验证**：手动运行 `python main.py`（需要配置环境变量），观察进程是否在业务完成后正常退出
- **Git 提交**：`fix: resource leak - add cleanup in main() to close httpx client and db connection`

### 步骤 4：修复 `tests/conftest.py` 的 `in_memory_db` fixture（P3 + P4）

- `depends_on: [步骤 2]`
- **问题类别**：测试基础设施修复
- **目标文件**：`tests/conftest.py`
- **描述**：

<aside>
⚠️

**核心问题**：当前 `_get_test_db` 每次被调用都新建一个 `aiosqlite.connect(":memory:")` 连接，且从不关闭。需要改为单例模式 + teardown 时关闭。

修改 `in_memory_db` fixture：

1. 将 `_get_test_db` 改为**单例模式**：在闭包中维护一个 `_conn` 变量，首次调用时创建连接并初始化表结构，后续调用直接返回同一个连接
2. 在 fixture 的 teardown 阶段（`yield` 之后），关闭这个连接（`await _conn.close()`）。由于 fixture 本身是同步的，改为 `async` fixture 或用 `asyncio.get_event_loop().run_until_complete()` 来执行关闭
3. 同时在 teardown 中重置 `core.db.db` 全局变量为 `None`，防止残留引用

1. 添加一个 `session` scope 的 fixture `_cleanup_global_resources`，设为 `autouse=True`
2. 该 fixture 在 yield 之后调用 `close_client()`（从步骤 1 新增的函数）关闭模块级 httpx 客户端
3. 同时调用 `close_db()` 作为兜底，确保即使有测试绕过 `in_memory_db` 直接触发了真实 DB 连接，也能被关闭

## 9. 修复决策说明

### 为什么选择显式 `close_*()` 函数而非 `async with` 上下文管理器？

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A：显式 close 函数**（采用） | 最小侵入，不改变现有单例模式；调用方可控关闭时机 | 需要调用方记得在退出时调用 |
| B：改为 `async with` 上下文管理器 | 自动管理生命周期 | 需要重构所有使用全局单例的模块，改为依赖注入，改动面大 |
| C：用 `atexit` 注册清理 | 无需修改 [main.py](http://main.py) | `atexit` 不支持 async 函数，需要额外处理事件循环 |

**Trade-off**：方案 A 是当前阶段最务实的选择。长期来看，若项目引入依赖注入框架或应用级生命周期管理（如 FastAPI 的 lifespan），可以迁移到方案 B。

### 为什么 `in_memory_db` 改为单例而非每次新建？

原始 `core.db._get_db()` 是单例模式，mock 也应保持相同语义。每次新建连接不仅导致泄露，还会使每次 `get_conn()` 操作不同的内存数据库实例，数据无法跨调用共享，这本身就是一个测试隔离性问题。
